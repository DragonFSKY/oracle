# 仓库审查提示词模块

仓库审计、Bug 根因、架构评估、实现计划或代码复审时，在 `prompt-core.md` 基础上选择本模块。不要默认进行与用户目标无关的全仓安全、性能或风格审计。

## 初始审查

Prompt 应提供：仓库/子目录身份、commit 或工作区状态、用户问题、相关症状、允许范围、非目标、当前设计文档、已执行测试及附件内容说明。

要求专家执行以下过程：

1. **读取覆盖**：确认实际可访问的关键入口、源码、测试、配置、迁移和构建文件；指出缺失、截断、冲突或无法判断权威性的材料。大型仓库只登记与目标有关的覆盖，不生成全文件清单。
2. **代码库模型**：建立相关模块职责、入口与调用链、数据流、状态所有权、错误传播、外部依赖和部署约束；提炼与目标直接相关的不变量。
3. **竞争性解释**：根因不明确时至少保留两个机制不同的解释，分别给出支持证据、反证和最小验证实验。明确根因时不要为了凑数强行生成路线。
4. **具体成果**：产出可检查的问题、反例、调用路径、实现方案、测试设计或验收矩阵，而不是泛泛报告。
5. **对抗性复核**：形成候选结论后，检查最可能误报的发现、遗漏的更简单根因、边界条件、错误入口、mock 遮蔽和过期文档。
6. **最小方案**：优先满足当前验收标准的最小可靠修改；只有现有结构直接阻止正确修复或验证时，才建议结构性重构。

高难且方向不明确时，要求维护 2–4 条机制不同的路线登记：核心机制、关键假设、已有证据、可立即执行的验证、精确缺口、失败原因和当前状态（继续 / 阻塞 / 合并 / 放弃）。仅仅换一种措辞不算新路线；缺口接近原问题难度时应标记阻塞并切换机制。

## 正式发现的证据门

每项确认问题至少包含：

- 严重程度和置信度；
- 相对路径与类、函数、方法或配置项；
- 从入口到问题位置的可达路径；
- 触发条件和实际影响；
- 支持证据及可能反驳它的证据；
- 最小验证实验或测试；
- 最小修复方向及影响范围。

没有可达路径或具体证据的内容只能进入“待验证假设”。不要仅因“不符合最佳实践”列为问题。

## 推荐输出

```text
1. Verdict 与执行摘要
2. 材料覆盖和缺失上下文
3. 相关架构、调用链和核心不变量
4. 已确认问题
5. 高置信度待验证问题
6. 被排除的根因及反证
7. 最小修复/实施顺序
8. 测试和验证计划
9. 修改影响与回滚注意事项
10. 后续观察
11. 验收标准逐项检查
```

## 专用追加模块

- Bug：从“外部症状 → 最后正确状态 → 第一次错误状态 → 状态写入者 → 入口”反向追踪。
- 安全：仅在用户要求时按“输入 → 解析 → 验证 → 权限 → 数据访问/修改 → 输出/日志”追踪信任边界。
- 性能：必须给可测指标、基线和实验，不能只凭代码形状定性。
- 重构：先列必须保持的不变量和影响图；能渐进修改时不建议整体重写。
