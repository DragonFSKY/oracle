# 审查—实施—回归闭环

用户要求“审查后修改”“修完再审”“回归审查”“最终验收”时使用。优先使用长阻塞 MCP：每次任务完成后立即进入下一阶段；工具 pending 时停止其他动作且不得轮询。MCP 未暴露或创建任务前启动失败时使用共享传输规则的异步 CLI 后备；CLI live 后结束当前轮，后续只对原 ID 做一次 `wait`，取回结果后继续下一阶段。

## 阶段和上限

```text
初始独立审查 → 本地核查与实施 → 新任务独立回归 → 必要时一次最终验收
```

默认最多三次专家审查：初审、回归、最终验收。`PASS` 立即结束；不得无限追问“还有吗”。

## 第一阶段：初审

使用 `prompt-core.md` 和适用的任务模块。要求专家给出证据、验收标准和最小实施顺序，不直接信任附件中的既有结论。

取回结果后，Agent 必须先在本地核对引用和可达路径。只有用户授权实施时才修改代码；不要机械采纳无证据、超范围或纯最佳实践建议。

## 第二阶段：实施证据

完成修改后，运行与改动风险匹配的真实测试，并生成简短的临时实施报告。报告至少包含：

- 原始目标和验收标准；
- 初审发现的采纳、拒绝或降级情况及理由；
- 修改的相对路径和关键符号；
- 根因与实际修复机制；
- 实际运行的命令和结果；
- 未运行的测试、剩余风险和环境限制；
- 当前 diff 基准或 commit 信息。

回归任务应附带修改后的冻结代码包、实施报告和可用的 diff/测试证据。证据文件使用临时路径，不要求写入用户仓库。

临时实施报告使用以下紧凑结构：

```text
# 实施证据

## 原始目标与验收标准
- [标准]：通过 / 未通过 / 未验证；证据

## 初审发现处理
- [发现编号]：采纳 / 拒绝 / 降级；理由和本地核查证据

## 实际修改
- 相对路径与关键符号：修改机制及原因

## 验证
- 实际命令：退出状态和关键结果
- 新增或修改的测试实际断言什么

## 未验证与剩余风险
- 未运行项、环境限制、已知不确定性

## 变更基准
- commit、工作区状态或 diff 身份
```

## 第三阶段：独立回归

必须使用新 `requestId`、新 Relay 任务和自足中文 prompt；不要延续初审对话，也不要把初审报告描述成可信结论。

回归 prompt 核心：

```text
你是独立回归审查者。初审报告、实施报告和修改结果均未经信任。
请从原始需求和验收标准重新建立判断，不要润色或延续原审查者的路线。

检查：
1. 原始需求是否逐项实现；
2. 初审问题是否解决根因，而非隐藏症状；
3. 修改是否破坏既有行为、兼容性、状态生命周期或部署流程；
4. 测试是否真正断言目标行为，mock 是否掩盖生产路径；
5. 是否存在未说明的范围扩张或无关重构；
6. 是否出现由本次 diff 引入的新高置信度问题；
7. 哪些结论仍需真实环境验证。

每项结论引用修改后快照中的相对路径和具体符号。
不得声称执行了附件没有证据证明的命令。

最终 verdict 只能是 PASS / CONDITIONAL PASS / FAIL / INSUFFICIENT EVIDENCE。
输出需求验收矩阵、初审发现关闭情况、新回归风险、测试证据评价和必须修复项。
达到 PASS 后明确结束，不要继续制造建议。
```

## 第四阶段：有限修正

- `PASS`：结束闭环。
- `CONDITIONAL PASS`：只修复明确列出的阻断项，再发起一次最终验收。
- `FAIL`：回到本地核查；只处理有证据且属于原目标的问题。重大方向错误可重新规划，但不得用原 slug 重复提交。
- `INSUFFICIENT EVIDENCE`：补充缺失证据后再验收，不凭猜测修改。

最终验收只检查原始标准、回归阻断项和修复引入的直接影响，不重新扩展成全仓审计。
