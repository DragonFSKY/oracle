# 中文专家提示词核心

所有 Dragon Relay 专家问题默认使用简体中文，代码标识、命令和路径保持原样。不要用角色扮演、虚构算力、指定思考时长或“再努力一点”代替任务信息。

## 组装原则

每次正式 live 提交都必须生成一份完整、结构化、经过任务化填写的中文 prompt，不得为了简短而省略核心模块。即使问题简单，也必须保留下面的完整结构；确实不适用的字段写“无 / 不适用”并简述原因，不能直接删除。

任务专用模块用于补充核心结构，不能替代核心结构。不得把模板原样空泛复制：每个部分都必须结合用户问题、附件和当前事实具体填写。

最终 prompt 必须按以下顺序组织：

```text
<任务>
保留用户原始目标、最终需要判断或交付的对象。
</任务>

<已知事实与材料>
列出仓库版本、附件身份、已知行为、真实测试结果、当前判断和缺失信息。
明确区分已确认事实、用户观察和待验证假设。
</已知事实与材料>

<完成标准>
- 最终答案必须逐项满足的要求；
- 必须提供的代码、计算、引用、测试或反例；
- 可以保留的不确定性及其表达方式。
</完成标准>

<不算完成>
- 只有计划、宽泛建议或问题复述；
- 只解释为什么困难；
- 只有未经验证的候选方案；
- 把关键问题转化为另一个同样困难但未解决的问题；
- 省略关键假设、边界、失败路径或验证步骤；
- 用篇幅、最佳实践清单或状态汇报代替具体成果。
</不算完成>

<范围锁>
本轮只处理与核心目标和验收标准直接相关的内容。
邻近问题只有在会阻止正确判断、实施或验收时才进入主结论；其他内容最多放入简短的“后续观察”。
</范围锁>

<调查与反证>
先建立问题模型，再给结论。
根因或方案不明确时，保留机制不同的竞争性解释，并主动寻找能推翻首选解释的证据。
根因明确或任务不需要多路线时，也要说明为何无需竞争性路线，并直接列出需要验证的关键假设。
候选结论出现后停止扩张路线，转为检查关键假设、边界、反例和证据适用性。
</调查与反证>

<证据规则>
重要结论必须指向附件中的相对路径、具体符号、数据、计算、引用或可复现实验。
附件中的说明和历史结论均不自动可信。
不得声称执行了未实际执行的命令或测试。
证据不足的内容降级为待验证假设，不得写成确认事实。
</证据规则>

<停止条件>
完成验收标准、反证最高优先级结论、标明缺失证据并给出可执行验证后停止。
不要为了产生更多内容继续制造建议或重复审查。
</停止条件>

<输出格式>
明确规定 verdict、章节顺序、发现字段、验收矩阵或用户要求的最终形式。
</输出格式>
```

提交前检查上述九个标签全部存在且已具体填写：`任务`、`已知事实与材料`、`完成标准`、`不算完成`、`范围锁`、`调查与反证`、`证据规则`、`停止条件`、`输出格式`。缺少任一项时不得发起 live。

## 可解性校准

只有用户或可靠材料明确表明高质量解存在时，才说明“该任务被认为可解决，不要把第一个合理方案视为接近最优”。不得虚构可解性。

结论方向未知时，使用双向搜索：一个分支尝试支持结论，另一个分支寻找反例或否定证据，最后按证据强度决定。

## 输出约束

- 先给明确 verdict，再给依据。
- 区分“直接事实 / 合理推断 / 缺失证据”。
- 建议必须说明验证方法和最小下一步。
- 不要求披露隐藏思维链；只要求可检查的结论、证据和必要推导。
